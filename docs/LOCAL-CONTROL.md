# 로컬 제어 페이지

기본 `http://127.0.0.1:18786/`에서 웹 서버가 설치된 PC의 연결을 관리합니다.
GUI 없는 Linux에서도 같은 웹 서버가 동작하며, 브라우저는 다른 PC에서 SSH 터널로 접속할 수 있습니다.
바탕화면의 `Caveman Control` 바로가기로도 열 수 있습니다.

## 설치

먼저 이 버전의 게이트웨이를 서버에 배포해야 압축 선택 기능을 사용할 수 있습니다.
서버에서 기존 `./stack update` 절차로 배포하고 로컬 저장소에서 `npm ci --ignore-scripts`를 실행합니다.
그다음 기존 native bridge 설치기를 같은 주소·키로 다시 실행해 브리지를 업데이트합니다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/install-native-bridge.ps1 -UpstreamUrl http://SERVER:18787/v1 -KeyFile C:/private/gateway-key
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/install-control-panel.ps1
```

관리 페이지는 `Caveman Local Control Panel` 로그인 작업으로 숨김 실행합니다.
모델 요청을 전달하는 `Caveman Native OpenAI Bridge`와 별도 프로세스이며 같은 비공개 설정을 사용합니다.
로그인 후에 시작하며 카탈로그 타이머를 등록하지 않습니다. 저장소와 Node 실행 파일 경로를 유지하세요.
페이지를 닫아도 진행 중인 서버 작업은 계속됩니다. 관리 프로세스 재시작 시 최근 작업 표시는 초기화되므로
서버 작업 로그와 현재 실행 버전을 확인한 뒤 다시 업데이트하세요.

Linux/WSL은 Node.js 22.13 이상과 systemd를 사용합니다. 저장소 의존성을 설치하고
브리지를 같은 주소·키로 재설치해 설정 실시간 반영 기능을 먼저 적용합니다.
관리 페이지를 사용자 서비스로 설치하려면:

```bash
node scripts/install-control-panel-linux.mjs --codex-home "$HOME/.codex"
# root 계정의 시스템 서비스
node scripts/install-control-panel-linux.mjs --codex-home /root/.codex --system --node-path /absolute/path/to/node
```

`caveman-control-panel.service`를 등록하고 웹 응답과 포트 소유 프로세스를 확인합니다.
시스템 서비스는 SSH 로그아웃과 무관하게 유지되고 재부팅 시 자동 시작합니다.
기존 서비스의 소유권이 다르거나 포트를 다른 프로세스가 사용하면 설치를 중단하며, 실패하면 이전 서비스를 복구합니다.
브리지 설정·로그인 파일은 설치기가 변경하지 않습니다. GUI·X11·Wayland는 필요하지 않습니다.
Linux 브리지 설치기는 코드 복사본을 사용하므로 Git 업데이트 후 설치기를 다시 실행해야 합니다.

### 다른 PC에서 Linux 제어 페이지 접속

웹 서버는 Linux의 `127.0.0.1`에만 바인딩합니다. 호스트 IP로 직접 접속하지 않고 SSH 터널을 사용합니다.
로컬 PC와 원격 서버의 포트가 같아야 Host·Origin 검사도 통과합니다.
현재 Windows의 `18786`과 함께 쓰는 경우, Linux 설정의 `controlPort`를 `18790`처럼 구분합니다.

```bash
ssh -N -L 127.0.0.1:18790:127.0.0.1:18790 USER@LINUX_HOST
```

SSH 연결을 유지한 채 브라우저에서 `http://127.0.0.1:18790/`를 엽니다.
이 페이지의 설정과 동기화 대상은 원격 Linux의 Codex 홈이며, Windows의 설정은 별개입니다.

## 연결과 압축

- Pod API 주소는 이 프로젝트로 배포된 게이트웨이의 `/v1` 주소입니다. 외부망에서는 신뢰할 수 있는 인증서의 HTTPS를 사용합니다.
- 인증키는 변경할 때만 입력합니다. 빈칸은 기존 키 유지이며, 키 값은 페이지에 다시 전달하지 않습니다.
- 저장 전에 인증·게이트웨이 기능·브리지를 확인합니다. 새 키는 별도 비공개 파일에 저장하고, 실패하면 이전 연결 설정으로 복구합니다.
- 브리지는 새 요청마다 설정을 읽습니다. 주소·키 변경 시 원격 복구 MCP 설정도 갱신하므로 실행 중인 Codex는 재시작해야 합니다.
- 압축 ON/OFF는 이 PC에서 보내는 새 모델 요청에 적용합니다. ON은 Caveman 경유, OFF는 OpenCodex 직결입니다. 계정 인증과 기존 원문 복구 기능은 유지합니다.
- 게이트웨이는 인증 후에만 압축 선택 헤더를 받아들이고, 내부 모델 서비스로 전달하기 전에 제거합니다.
- 기존 요청이 이미 처리 중이면 해당 요청의 경로는 바뀌지 않습니다.

## 모델 목록

`지금 동기화`는 서버 카탈로그를 이 Codex 홈에 내려받습니다. 변경 없는 경우 파일을 다시 쓰지 않습니다.
`서버 카탈로그 먼저 갱신`은 설정된 관리 연결(SSH 또는 같은 Linux 서버 직접 관리)로 카탈로그를 갱신합니다. 이후 로컬 동기화를 실행합니다.
`연결 진단`은 브리지·로그인 메타데이터·카탈로그·복구 MCP를 확인하며 모델 추론은 하지 않습니다.

## 서버 업데이트

페이지의 SSH 설정에 서버 대상, 로컬 개인키 파일 경로, 서버 스택 디렉터리를 지정합니다.
SSH 호스트는 Pod 주소의 호스트와 같아야 합니다. SSH는 비대화형 키 인증과 엄격한 known_hosts 검사를 사용합니다.
비밀번호나 원격 명령을 웹 입력으로 받지 않습니다. 관리 연결은 일반 API 게이트웨이 키와 별도입니다.

웹 서버와 Podman이 **같은 Linux 저장소**에서 실행되는 경우에는 설치 시 비공개 설정에
`management: {"mode":"local","repo":"/실제/설치/저장소"}`를 지정할 수 있습니다.
이 모드는 같은 저장소의 정해진 Python 관리 작업만 실행하므로 자신에게 SSH로 접속하거나
SSH 개인키를 복사할 필요가 없습니다. 화면에는 Linux 서버 직접 관리로 표시됩니다.
HTTP 설정 API로 이 모드를 새로 켜거나 경로를 바꿀 수는 없습니다. 다른 서버를 관리하려면 기존 SSH 방식을 사용합니다.
직접 관리 모드에서는 Pod 주소도 설치된 서버로 고정하여 화면의 연결 대상과 업데이트 대상이 달라지지 않게 합니다.

`버전 확인`은 실행 중인 컨테이너의 패키지 버전과 npm의 최신 안정 버전을 조회합니다.
`업데이트`는 선택한 구성 요소와 명시한 버전에 대해서만 실행합니다.

1. 서버 작업 잠금과 디스크 여유 공간 확인.
2. 실행 중인 컨테이너의 package.json/package-lock.json을 비공개 백업 디렉터리에 보관.
3. 임시 디렉터리에서 선택 버전의 lockfile 생성. 패키지 lifecycle script는 실행하지 않음.
4. 기존 `stack update`로 이미지 빌드, 데이터 백업, 후보 컨테이너·카탈로그 검사 후 적용.
5. 운영 전환 실패의 이미지·상태 복원은 기존 `stack update`가 처리. Git manifest는 변경하지 않음.

이 과정은 서버를 공유하는 모든 클라이언트에 영향을 주며 일시적인 연결 중단이 있습니다.
최신 버전 표시가 호환성을 보장하지는 않습니다. 후보 검사는 기동과 카탈로그를 확인하며 모든 모델·도구의
의미적 호환성을 보장하지 않습니다. 업데이트 후 연결 진단과 필요한 모델 사용을 확인하세요.
Caveman engine 버전은 선택한 CLI의 설치기가 결정합니다.

업데이트는 **현재 실행 중인 버전을 기준으로 선택한 구성 요소만 변경**합니다. 다른 구성 요소를
Git의 예전 고정 버전으로 되돌리지 않습니다. Git manifest는 보존하고 정확한 새 manifest/lockfile과
적용 결과는 `data/releases/control-<작업 ID>/`에 기록합니다. 실행 버전이 같으면 재빌드하지 않습니다.
서버의 `stack`도 함께 업데이트해야 이 임시 빌드 컨텍스트 방식을 사용할 수 있습니다.
서버 소스·게이트웨이 자체의 Git 업데이트는 이 두 패키지 버튼의 대상이 아닙니다.

로그는 서버 `data/control-jobs/<작업 ID>.log`, manifest 백업은 `backups/control-manifests-<작업 ID>/`에 있습니다.
실패 시 원인을 확인하고 필요하면 기존 `stack rollback` 절차를 사용합니다. 원시 로그는 웹에 노출하지 않습니다.

## 접근 범위

페이지는 IPv4 loopback에만 바인딩하고 Host·Origin·브라우저 요청 출처·CSRF 토큰을 확인합니다.
웹 페이지에는 외부 스크립트나 폰트를 사용하지 않습니다. 관리 포트를 LAN이나 인터넷으로 공개하지 마세요.
같은 OS 사용자 권한으로 실행하는 프로그램까지 격리하는 기능은 아닙니다.

2026-10-06 검증: Windows Node 75개 통과(환경별 2개 건너뜀), WSL 관련 32개 및 Python 6개 통과.
실제 서버에서 압축 ON/OFF 모델 응답, 카탈로그 동기화·서버 갱신, MCP 진단, 버전 조회, 동일 버전 업데이트 건너뛰기를 확인했습니다.
새 upstream 버전으로의 실제 업그레이드는 수행하지 않았습니다. 기존 게이트웨이 변경은 후보 검사를 거쳐 배포했습니다.

2026-10-13 검증: GUI 없는 원격 Linux에 root 시스템 서비스를 실제 설치했습니다. 페이지 응답,
브리지·게이트웨이 상태, 웹 연결 진단과 복구 MCP, 서버 카탈로그 갱신, 클라이언트 동기화,
실행 버전·최신 버전 조회를 확인했습니다. 서비스 재시작 후 다시 응답하며 자동 시작도 활성화했습니다.
호스트 전체 재부팅과 장시간 패키지 업그레이드는 이번 검증에 포함하지 않았습니다.
Linux/WSL 관련 자동 테스트 18개가 통과했습니다. 원격 브라우저 접속은 위 SSH 터널 절차가 필요합니다.
