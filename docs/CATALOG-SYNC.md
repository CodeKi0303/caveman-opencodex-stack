# 카탈로그 갱신과 클라이언트 동기화

동기화를 실행하면 **현재 OpenCodex 목록 확인 → 서버 스냅샷/ETag → 클라이언트 카탈로그·설정·캐시 검사** 순서로 진행합니다.
서버와 로컬 카탈로그가 같다는 이유로 나머지 검사를 생략하지 않습니다. 정기 실행 타이머는 기본으로 등록하지 않습니다.

## 실행 방법과 범위

| 실행 위치/명령 | 처리 범위 |
|---|---|
| 웹 `지금 동기화` | 현재 PC만. 서버의 최신 목록 확인 후 로컬 파일 검사·복구 |
| `npm run sync`, `manual-sync.mjs`, Windows `Sync-Catalog.vbs` | 지정된 현재 Codex 홈만. WSL과 Windows 홈은 별개 |
| 웹 `서버 갱신 + PC 동기화` | 서버 갱신 → 현재 PC → 같은 Pod에 연결된 등록 SSH PC |
| 웹 서버 소프트웨어 업데이트 | 서버 작업 성공 후 위와 같은 PC 동기화. 이미 같은 버전이어도 동기화 |
| SSH PC 관리의 `모델 목록 동기화` | 선택한 각 PC가 자신의 현재 Pod에서 목록 확인·동기화 |
| `./stack catalog`·`update`·`git-update` 직접 실행 | 서버 작업과 스냅샷 갱신. PC 등록 목록에 접근하지 않음 |
| `./manage`의 Git 업데이트 | 서버 업데이트 후 현재 사용자의 연결·카탈로그 재적용 |

웹 연계 작업은 해당 관리 페이지 옆 `remote-clients.json`에 등록된 PC를 사용합니다.
다른 Pod에 연결된 PC는 자동 연계 대상에서 건너뛰고, 현재 제어 서비스가 SSH 대상으로 중복 등록돼 있으면 로컬 처리 결과를 사용합니다.
원격 제어 서비스에도 캐시 복구 기능이 있어야 하므로 기능 확인에 실패하면 해당 PC 업그레이드를 안내합니다.

## 서버가 오래된 목록을 반환하지 않도록 처리

게이트웨이는 인증된 `/v1/catalog` GET·HEAD를 받으면 먼저 내부 OpenCodex의 `/v1/models` 응답을 검증합니다.
정상 목록으로 서버 스냅샷을 원자적으로 갱신한 다음, 클라이언트의 `If-None-Match`와 ETag를 비교합니다.
목록이 같으면 `304`, 바뀌었으면 새 본문과 ETag를 반환합니다. 동시에 들어온 요청은 진행 중인 갱신을 공유합니다.

OpenCodex에 연결할 수 없거나 목록이 유효하지 않으면 `503`을 반환하고 마지막 정상 스냅샷을 유지합니다.
갱신에 실패한 오래된 목록을 최신이라는 `304` 응답으로 처리하지 않습니다. 클라이언트도 이 실패에서 기존 파일을 보존합니다.
페이지의 10초 상태 조회 자체는 모델 목록 동기화를 실행하지 않습니다.

## `models_cache.json`과 사용자 지정 카탈로그

이 프로젝트는 `model_catalog_json`으로 `opencodex-catalog.json`을 지정합니다.
Codex의 네이티브 캐시 이름은 **`models_cache.json`**이며, `model_cache.json`이 아닙니다.
두 파일은 목적이 다르므로 모델 행과 컨텍스트 값이 항상 같아야 하는 것은 아닙니다.

- `opencodex-catalog.json`: 서버에서 받은 사용자 지정 모델 정보. Codex는 설정에 지정된 이 파일을 시작할 때 읽습니다.
- 정상 네이티브 캐시: Codex가 직접 저장한 모델 정보와 조회 시각·클라이언트 버전·ETag·identity. 스택은 내용이 달라도 원본 바이트를 보존합니다.
- 스택의 호환 스냅샷: `fetched_at=2000-01-01T00:00:00Z`, `client_version=0.0.0`으로 구분합니다. 네이티브 캐시를 최신으로 가장하지 않으며 인증 identity를 생성하지 않습니다.

`sync`는 목록이 같은 `200`/`304`에서도 캐시가 없거나, 빈 파일/빈 모델 배열이거나, 손상된 경우 복구합니다.
기존 호환 스냅샷의 모델이 오래됐으면 갱신합니다. 또한 유효한 `model_catalog_json` 경로를 점검·복구합니다.
provider 주소·인증·MCP 설정은 바꾸지 않습니다. 변경 파일만 보호된 백업에 저장하고 원자적으로 교체하며,
정상인 항목만 있는 재실행은 쓰기·백업을 생략합니다.

설치된 Windows Codex `0.167.0-alpha.4.1`을 별도 임시 홈에서 검증했을 때,
정상 사용자 지정 카탈로그는 네이티브 캐시가 없거나 비었거나 다른 내용이어도 동일하게 로드됐습니다.
따라서 빈 캐시 자체를 현재 빌드의 모델 목록 누락 원인으로 단정하지 않습니다.
화면에 다른 모델이 보이면 실제 Codex 홈, 선택 프로필의 카탈로그 경로, 설정 적용 후 앱 재시작 여부도 확인합니다.
[OpenAI Docs의 로컬 카탈로그와 시작 시 로딩 설명](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway)을 참고하세요.

## 결과와 재시도

CLI·더블클릭 GUI·웹 결과는 **모델 목록 갱신 / Codex 캐시 복구 / 카탈로그 설정 경로 복구 / 변경 없음**을 구분합니다.
`doctor`는 클라이언트 파일을 수정하지 않고 캐시 복구 필요 여부도 보여 줍니다.
정상 네이티브 캐시와 사용자 지정 목록의 차이는 참고 정보이며 그 차이만으로 캐시를 덮어쓰지 않습니다.

웹에서 서버 작업은 성공했지만 일부 PC 동기화가 실패하면 **부분 완료**와 PC별 결과를 표시합니다.
서버 작업 성공을 취소하거나 다른 PC의 성공한 변경을 되돌리지 않습니다. 실패한 PC의 SSH·제어 서비스·버전을 확인하고 동기화를 재시도하세요.
서버 작업 자체가 실패하면 후속 PC 동기화를 실행하지 않습니다.

브라우저 페이지를 닫아도 실행 중인 제어 서비스가 후속 작업을 계속합니다.
제어 서비스 자체를 종료·재시작하면 독립 서버 작업은 계속될 수 있지만 후속 PC 동기화가 자동 재개되지는 않습니다.
서버 작업 기록·실행 버전을 확인한 뒤 **서버 갱신 + PC 동기화**로 후속 처리를 다시 실행하세요.

카탈로그나 설정 변경 후 실행 중인 Codex에 새 정보가 필요하면 재시작 안내가 표시됩니다.
파일 동기화가 기존 프로세스의 메모리를 즉시 바꾸는 것은 아니며, 스택은 Codex를 자동 종료하지 않습니다.
