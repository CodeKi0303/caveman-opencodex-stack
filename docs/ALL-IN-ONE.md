# Linux·WSL 올인원 설치와 관리

Linux 터미널에서 `./manage`를 실행하고 메뉴를 선택합니다. 처음에는 설치를 안내하고, 이후에는
저장된 주소·키 파일·포트·Codex 홈을 사용합니다. GUI 없는 원격 Linux에서도 설치와 운영을 완료할 수 있으며
기존 웹 제어 페이지도 함께 설치됩니다.

이 문서는 아직 `main`에 병합되지 않은 `feature/all-in-one-linux` 브랜치 기준입니다.

## 시작 명령

**Codex를 사용할 Linux 사용자로** 실행합니다. 원격 Linux라면 먼저 그 사용자로 SSH 접속하고,
WSL이라면 해당 배포판의 터미널을 엽니다.

```bash
git clone --branch feature/all-in-one-linux \
  https://github.com/CodeKi0303/caveman-opencodex-stack.git caveman-podman
cd caveman-podman
./manage
```

첫 메뉴의 **1번**을 고른 뒤 아래 두 방식 중 하나만 선택하면 됩니다. 설치기는 추천 포트를 제시하고
키 파일·설정 경로·자동 시작 서비스를 연결합니다. 이후 질문에 답하면 로그인과 연결 진단까지 이어집니다.
완료 후 **10번 `Codex 실행`**을 선택하면 작업을 시작할 수 있습니다. 별도 설정 파일 편집이나
서비스 등록 명령, 전역 Codex 설치는 필요하지 않습니다.

시작 전에 Git과 Python 3.11 이상이 필요합니다. 실행기는 Linux용 Node가 없거나 지원 버전보다 낮으면
공식 Node.js 24.14.1을 사용자 폴더 `~/.local/share/caveman-client/node-runtime`에 설치할지 묻습니다.
다운로드 체크섬을 확인하며 시스템 Node는 변경하지 않습니다. 프로젝트 의존성 준비도 확인 후 수행합니다.
이미 설치된 Node는 22.13 이상을 사용하며 Windows의 `node.exe`는
WSL 실행 환경을 대신할 수 없습니다. 서버에 필요한 Podman 4.9.3+, Python 3.11+, slirp4netns와 systemd도
확인합니다. 지원하는 배포판에서는 패키지 관리자 설치를 선택할 수 있지만, 설치 후에도 최소 버전에
미달하면 진행을 중단합니다. systemd가 꺼진 WSL은 먼저 systemd를 활성화하고 배포판을 다시 시작해야 합니다.

WSL의 저장소는 `/home/사용자/caveman-podman`처럼 Linux 파일시스템에 둡니다.
서비스는 실제 Node·저장소 경로를 사용하므로 설치 이후 해당 파일을 이동하거나 지우지 마세요.

## 시나리오 1: 이 Linux에 서버까지 설치

원격 Linux에 서버를 새로 만들거나 WSL 안에서 전체 구성을 실행할 때 선택합니다.

1. `올인원 설치 / 연결 설정`에서 **이 Linux에 전체 서버 설치**를 선택합니다.
2. 표시된 Linux 사용자와 Codex 홈을 확인합니다. 기본은 현재 사용자의 `~/.codex`입니다.
3. 모델 API를 이 PC에서만 사용할지, 다른 PC에서도 접속할지 선택합니다. 새 설치의 OpenCodex
   관리자 화면은 어느 경우에도 Linux의 `127.0.0.1`에만 바인딩합니다. 서버 포트와 브리지·웹 포트는
   추천값을 제시하며 기존 `.env`와 클라이언트 설정이 있으면 저장된 값을 유지합니다.
4. 설치 내용을 확인하면 필요한 서버 키와 설정을 만들고 Podman 서버를 빌드·시작합니다.
   브리지·웹 제어·서버 자동 시작 서비스도 등록하고 Codex 연결과 카탈로그를 구성합니다.
5. 로그인 메뉴에서 **Codex 디바이스 로그인**을 진행합니다. 터미널에 표시되는 주소를 다른 PC의
   브라우저에서 열고 코드를 입력하면 됩니다. 이미 같은 Linux 사용자에게 로그인했다면 재로그인은 선택입니다.
6. `연결 진단` 결과를 확인한 뒤 **10번 `Codex 실행`**을 선택합니다. 기존 Codex 프로세스가 있었다면 재시작합니다.

게이트웨이 키와 관리자 키는 서버에서 자동으로 생성하고 기존 키가 있으면 보존합니다.
CLI는 생성된 게이트웨이 키 파일을 자동으로 연결하므로 컨테이너에 들어가 키를 찾아 복사할 필요가 없습니다.
같은 Linux의 서버 관리는 로컬 관리 모드를 사용하며 SSH 개인키를 요구하지 않습니다.

첫 빌드는 저장소가 고정한 패키지 버전을 사용합니다. 설치 질문에서 최신 안정 버전 적용을 선택하면
첫 기동 후 Caveman·OpenCodex·컨테이너 Codex를 최신 안정 버전으로 갱신합니다.
나중에는 `Git + 최신 업데이트`를 선택합니다. 깨끗한 Git 작업 트리에서 추적 브랜치의 소스를 가져온 뒤
최신 안정 패키지를 조회하고 기존 후보 검증·백업 절차를 거쳐 적용합니다. 새 Git 코드의 의존성을 준비하고
브리지·웹 서비스도 다시 적용합니다.

## 시나리오 2: WSL·Linux에서 기존 서버 사용

예를 들어 서버는 `192.168.50.61`에 있고 WSL의 Codex를 연결할 때 선택합니다.

1. `올인원 설치 / 연결 설정`에서 **기존 서버에 클라이언트 연결**을 선택합니다.
2. 서버 주소를 입력합니다. 예: `http://192.168.50.61:18787/v1`.
3. 서버의 **게이트웨이 키**를 숨김 입력하거나, 이 Linux에 보관한 키 파일을 선택합니다.
   기존 연결을 다시 설정할 때는 저장된 키를 유지할 수도 있습니다.
4. 추천 브리지·웹 포트를 확인하고 설치합니다. Podman 서버는 이 환경에 새로 만들지 않습니다.
5. 이 Linux 사용자에게 Codex 디바이스 로그인을 진행하고 연결 진단을 확인한 뒤 **10번 `Codex 실행`**을 선택합니다.

첫 연결에는 서버 주소와 게이트웨이 키가 필요합니다. 관리자 토큰이나 서버의 SSH 개인키는
일반 모델 연결에 사용하지 않습니다. CLI가 SSH로 키를 자동 수집하지도 않습니다.
키를 터미널 명령 인수에 붙이거나 Git에 저장하지 마세요.

이 모드의 카탈로그 동기화·압축 선택·로그인 대상은 **현재 Linux 사용자**입니다.
Windows Codex와 다른 WSL 배포판의 설정은 각각 별개입니다. 압축 원문 DB와 서버 모델 목록은 같은
서버를 사용하는 개인 클라이언트들이 공유하지만, 클라이언트 설정이 자동으로 서로 복제되지는 않습니다.

## 일상적인 사용

같은 사용자·저장소에서 다시 실행합니다.

```bash
./manage
```

| 메뉴 | 하는 일 |
|---|---|
| 올인원 설치 / 연결 설정 | 새 전체 서버 설치 또는 기존 서버 연결·기존 설정 재적용 |
| 상태 / 웹 주소 | 서비스와 연결 상태, 현재 사용자의 웹 주소·SSH 터널 방법 표시 |
| Codex 디바이스 로그인 | 현재 Codex 홈에 로그인; 다른 사용자의 인증은 복사하지 않음 |
| 연결 진단 | 브리지·서버 카탈로그·복구 MCP와 로그인 메타데이터 확인 |
| 수동 동기화 | 서버 카탈로그를 현재 Codex 홈으로 다운로드 |
| 압축 ON/OFF | 이 클라이언트의 새 모델 요청에 Caveman 사용 여부 적용 |
| 서버 버전 조회 | 로컬 서버 또는 기존 SSH 관리 연결의 실행 버전·최신 안정 버전 확인 |
| Git + 최신 업데이트 | 이 저장소의 로컬 서버 소스·서버 패키지 업데이트 |
| 재시작 | 브리지·Codex 연결·웹 설치 재적용. 로컬 서버 모드에서는 Podman 서버 재시작도 선택 가능 |
| 10 Codex 실행 | 저장소에 설치된 Codex CLI를 관리 중인 Codex 홈으로 실행 |
| 종료 | 메뉴 종료; 이미 등록된 서비스는 계속 실행 |

`Codex 실행`은 작업 폴더를 물은 뒤 이 프로젝트의 npm 의존성으로 준비된 CLI를 실행하고, 현재 관리 중인
`CODEX_HOME`을 전달합니다. 기본 작업 폴더는 현재 디렉터리입니다. 기존 전역 Codex 설치나 다른 사용자의 로그인은 변경하지 않습니다.

원격 서버에 연결한 클라이언트 모드에서는 이 저장소의 Git 메뉴로 원격 서버를 업데이트하지 않습니다.
서버에 접속해 같은 메뉴를 실행하거나, 웹 제어 페이지에 별도 SSH 관리 연결을 설정합니다.
새 클라이언트 연결은 SSH 관리를 자동 구성하지 않으므로 버전 조회에서도 관리 연결이 필요하다고 안내합니다.
모델 연결·압축 선택·카탈로그 동기화는 SSH 관리 연결 없이 사용할 수 있습니다.
웹의 Caveman/OpenCodex 개별 업데이트와 CLI의 Git 소스·최신 버전 업데이트는 적용 범위가 다릅니다.

설치·재시작은 정기 카탈로그 예약을 만들지 않습니다. 필요할 때 메뉴의 수동 동기화 또는 웹의
`지금 동기화`를 사용합니다. 카탈로그가 바뀌면 Codex를 재시작해야 새 목록을 읽습니다.
서버 업데이트는 연결된 모든 클라이언트에 영향을 주며 전환 중 잠시 연결이 끊길 수 있습니다.
호스트의 Node·Codex CLI·Codex Desktop 업그레이드는 서버 패키지 업데이트에 포함하지 않습니다.

## 웹 제어 페이지 접속

설치 마지막 화면과 `상태 / 웹 주소` 메뉴의 주소를 사용합니다. 다음은 신규 설치 추천값이며,
기존 설치·포트 선택에 따라 달라집니다.

| 위치 | 브리지 포트 | 웹 제어 포트 |
|---|---:|---:|
| 일반 Linux | 18788 | 18790 |
| WSL | 18789 | 18791 |

웹 서버는 `127.0.0.1`에서만 실행합니다. 원격 Linux에서는 **브라우저를 사용할 PC**에 아래처럼
SSH 터널을 열고 유지합니다. 실제 접속 계정·호스트와 설치 시 표시된 포트를 사용하세요.

```bash
ssh -N -L 127.0.0.1:18790:127.0.0.1:18790 USER@LINUX_HOST
```

브라우저에서 `http://127.0.0.1:18790/`를 엽니다. Host·Origin 검사 때문에 양쪽 포트가 같아야 합니다.
이미 Windows에서 같은 포트를 사용한다면 신규 Linux 설치 메뉴에서 다른 웹 포트를 지정하고 양쪽에 똑같이 적용합니다.
WSL은 배포판이 실행 중인 동안 Windows 브라우저에서 `http://127.0.0.1:18791/`로 접속합니다.

이 웹 페이지는 OpenCodex 관리자 화면과 별개입니다. 기본 서버 API 포트는 `18787`, OpenCodex 관리자
포트는 `20100`입니다. 새 설치의 관리자 화면은 loopback 전용이므로 원격에서 필요하면 별도 SSH 터널을
사용합니다. 기존 설치의 바인딩은 보존합니다. 웹 제어 페이지를 LAN이나 인터넷으로 직접 공개하지 않습니다.

## 사용자·자동 시작·인증 범위

일반 사용자로 실행하면 사용자 systemd 서비스와 rootless Podman을 사용합니다. root로 실행하면
시스템 서비스와 root의 Podman 저장소를 사용합니다. 둘은 컨테이너·키·Codex 홈이 서로 다릅니다.
기존 설치를 관리할 때 계정을 바꾸거나 무작정 `sudo ./manage`를 붙이지 마세요.

시스템 서비스는 Linux 부팅 때 시작합니다. 일반 사용자 서비스가 로그아웃 후에도 필요하면 설치 과정의
linger 활성화를 선택합니다. 전체 서버와 클라이언트 전용 설치 모두 이 선택을 제공하며,
클라이언트 전용 설치의 기본 선택은 활성화하지 않음입니다. WSL은 **배포판 자체가 먼저 실행돼야** systemd 서비스가 시작됩니다.
이 CLI는 Windows 부팅 시 WSL을 여는 예약을 만들지 않습니다.

| 인증 정보 | 목적과 보관 위치 |
|---|---|
| 게이트웨이 키 | 모델·카탈로그·복구 MCP 접근. 서버 `secrets/gateway-key` 및 연결한 사용자의 비공개 설정 |
| 관리자 키 | OpenCodex 관리자 화면 로그인. 서버 `secrets/admin-key`; 일반 클라이언트에 배포하지 않음 |
| Codex 로그인 | 사용자의 모델 인증. 해당 Linux 사용자의 Codex 홈에 저장; 컨테이너로 복사하지 않음 |
| SSH 개인키 | 다른 PC에서 터널 또는 원격 관리를 할 때 사용. 로컬 서버 직접 관리에는 불필요 |

같은 게이트웨이 키의 원문 복구 DB에는 사용자별 격리가 없습니다. 이 구성은 한 개인이 여러 클라이언트를
연결하는 용도이며 다른 사용자까지 분리하려면 별도 컨테이너·키·포트·데이터 디렉터리가 필요합니다.

## 명령 옵션과 문제 확인

```bash
./manage --help
./manage --status
./manage --setup
./manage --codex-home /absolute/path/.codex --user
# root가 자신의 기존 시스템 서비스를 관리할 때
./manage --codex-home /root/.codex --system
```

`--setup`은 설치 마법사를 마치면 종료합니다. 옵션이 없으면 메뉴가 유지됩니다.
Linux의 npm을 사용할 수 있다면 `npm run manage`로도 같은 준비·설치 메뉴를 실행할 수 있습니다.
`--help`와 `--status`는 런타임이나 의존성을 새로 설치하지 않습니다.

다른 프로그램이 포트를 사용하거나 기존 서비스의 소유권을 확인할 수 없으면 설치를 중단합니다.
해당 프로세스를 임의로 종료하지 말고 표시된 경로와 포트를 확인하세요. Git 업데이트가 미커밋 변경 때문에
중단되면 변경 사항을 검토·커밋한 다음 다시 실행합니다. 자동으로 reset하거나 stash하지 않습니다.
설치 중 오류가 나면 이미 동작하는 서버·로그인 파일을 지우지 말고, 표시된 오류와 백업 위치를 확인한 뒤
